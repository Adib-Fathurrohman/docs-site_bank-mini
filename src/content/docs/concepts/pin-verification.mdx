PIN nasabah adalah 6 digit angka. PIN dipakai untuk membuka kunci sesi aplikasi (unlock),
mengotorisasi penarikan, dan mengganti PIN. **PIN bukan kredensial login** (login menggunakan
autentikasi Firebase). Semua pemeriksaan PIN berjalan di **satu tempat**:
`App\Services\PinService::verify()`.

## Penyimpanan dan kepemilikan

- `customers.pin` di-cast `hashed` (bcrypt, `BCRYPT_ROUNDS=12`) dan termasuk atribut
  tersembunyi (`$hidden`). Tidak ada resource, pesan error, atau log yang memuat PIN.
- Kolom `pin` bernilai **nullable**: rekening baru dibuat tanpa PIN (`pin_set: false`).
- Database menerapkan constraint `CHECK (pin IS NULL OR activated_at IS NOT NULL)`: PIN
  hanya boleh ada jika rekening sudah diaktifkan.
- **Admin tidak pernah menetapkan PIN.** PIN dibuat sendiri oleh nasabah di aplikasi mobile
  setelah aktivasi (`POST /api/customer/pin/setup`) dengan menyertakan token Firebase segar
  sebagai bukti kepemilikan.
- Sebelum nasabah membuat PIN, semua operasi yang membutuhkan PIN ditolak dengan status **422**
  dan kode error `pin_not_set` tanpa mencatat kegagalan.
- **Dua jalur penanganan Lupa PIN:**
  1. **Reset Langsung oleh Admin:** Admin mereset PIN melalui portal admin (`POST /api/admin/customers/{id}/pin-reset`). PIN dan status blokir dihapus seketika, dan permintaan mandiri yang terbuka otomatis dibatalkan.
  2. **Permohonan Mandiri (Self-Service v0.2.1):** Nasabah mengajukan reset di aplikasi (`POST /api/customer/pin-reset-requests`) dengan re-autentikasi Firebase. Permohonan wajib disetujui admin dan memiliki masa tunggu pengamanan 24 jam (`BANK_PIN_RESET_WAIT_HOURS`) sebelum PIN baru dapat dibuat. Selama proses ini berlangsung, seluruh penarikan tunai dijeda (**422** `pin_reset_in_progress`).

## Blokir PIN bersama

| Aturan | Nilai |
| --- | --- |
| Kesalahan sebelum blokir | 3 berturut-turut (`BANK_PIN_MAX_ATTEMPTS`) |
| Lama blokir | 15 menit (`BANK_PIN_LOCK_MINUTES`) |
| Berlaku di | Buka kunci aplikasi (unlock), persetujuan penarikan di aplikasi, penarikan PIN di loket, ganti PIN |
| Reset penghitung | PIN benar, atau admin melakukan reset PIN |
| Kolom | `pin_failed_attempts`, `pin_locked_until` |

`PinService::verify()` berjalan dalam **transaksi database sendiri** dengan row lock
pada nasabah, sehingga percobaan yang salah tetap tersimpan walaupun permintaannya
gagal. Pemanggil yang punya transaksi lebih besar (persetujuan, penarikan di loket)
memanggilnya **sebelum** transaksi itu.

<Aside type="caution" title="Satu blokir untuk semua tempat">
Tiga PIN salah saat unlock aplikasi juga memblokir persetujuan penarikan dan penarikan di loket teller.
</Aside>

### Respons saat PIN salah atau belum dibuat

Ketika PIN belum dibuat (`pin_set: false`):

```json title="422 Unprocessable Entity"
{
  "message": "Nasabah belum membuat PIN. PIN dibuat oleh nasabah di aplikasi Bank Mini setelah akun diaktifkan.",
  "code": "pin_not_set"
}
```

Ketika PIN salah:

```json title="422 Unprocessable Entity (percobaan 1 atau 2)"
{ "message": "PIN salah. Sisa percobaan: 2.", "remaining_attempts": 2, "pin_locked_until": null }
```

Saat diblokir (`pin_locked_until` dalam UTC, pesan dalam WIB):

```json title="422 Unprocessable Entity (diblokir)"
{
  "message": "PIN diblokir sementara karena terlalu banyak percobaan salah. Coba lagi pukul 20:25.",
  "remaining_attempts": 0,
  "pin_locked_until": "2026-10-27T13:25:37.830610Z"
}
```

## Dua mode otorisasi penarikan

Setiap penarikan butuh PIN nasabah. **Siapa yang mengetik PIN dan di perangkat mana**
ditentukan oleh pengaturan `withdrawal_verification`.

| Mode | Nilai pengaturan | Cara kerja | Endpoint |
| --- | --- | --- | --- |
| **A · Persetujuan di aplikasi** (bawaan) | `mobile` atau `both` | Teller membuat permintaan; nasabah menyetujuinya dengan PIN di HP sendiri; teller menyelesaikannya. Teller tidak pernah melihat atau mengirim PIN | `/api/teller/withdrawal-authorizations`, `/api/customer/withdrawal-authorizations` |
| **B · PIN di loket** | `terminal` atau `both` | Nasabah mengetik PIN di layar teller; penarikan berjalan dalam satu permintaan | `POST /api/teller/withdrawals` |

Mode B mati secara bawaan karena PIN melewati klien teller. Mode B juga punya
keterbatasan **L2**: PIN diperiksa sebelum status shift, rekening, dan saldo, sehingga
PIN salah tetap dihitung walaupun penarikan pasti gagal karena alasan lain. Mode A
tidak punya masalah ini karena semuanya diperiksa saat permintaan dibuat.
