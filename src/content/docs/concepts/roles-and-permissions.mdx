## Empat lapisan pemeriksaan

| Lapisan | Pertanyaan | Tempat | Jika gagal |
| --- | --- | --- | --- |
| **Autentikasi** | Siapa yang memanggil? | `auth:sanctum` di setiap route kecuali login | `401 Unauthenticated.` |
| **Otorisasi** | Bolehkah aktor/peran ini memanggil endpoint ini? Apakah data ini miliknya? | Middleware `staff`, `staff:{peran}`, `customer`; cek kepemilikan di controller | `403` (peran) atau `404` (bukan miliknya) |
| **Aturan bisnis** | Bolehkah aksi ini dalam keadaan sekarang? | Service (status shift, saldo, PIN, status laporan, …) | `422` |
| **Tampilan klien** | Menu dan tombol apa yang ditampilkan? | Kode React / Expo | — |

<Aside type="danger" title="Menyembunyikan tombol bukan pengamanan">
Setiap permintaan diperiksa ulang oleh backend terhadap database (peran dan
`is_active` dibaca baru untuk setiap token). Klien hanya meniru aturan backend agar
pengguna tidak melihat halaman yang pasti gagal.
</Aside>

## Aktor dan model

Staf dan nasabah adalah **tabel dan model yang berbeda**. Nasabah bukan baris di
tabel `users` dan tidak punya `role`.

| Aktor | Model | Nilai `role` | Catatan |
| --- | --- | --- | --- |
| Administrator | `App\Models\User` | `admin` | Dibuat oleh seeder; tidak dapat dibuat, diubah, diblokir, atau dihapus lewat API |
| Supervisor | `User` | `supervisor` | |
| Teller | `User` | `teller` | Biasanya siswa yang bertugas (kolom `class`, `phone`) |
| Nasabah | `App\Models\Customer` | — | Siswa; login menggunakan Firebase (Google atau email/password), aktivasi rekening via NIS |

Setiap staf punya tepat satu peran. Pengguna dengan banyak peran tidak didukung.

## Middleware

| Middleware | Kelas | Efek |
| --- | --- | --- |
| `auth:sanctum` | Laravel Sanctum | Butuh token bearer valid dan belum kedaluwarsa. Jika tidak: `401 {"message":"Unauthenticated."}` |
| `staff` | `EnsureStaffRole` | Token harus milik `User` dengan `is_active = true`. Jika tidak: `403 "Fitur ini khusus untuk staf bank."` atau `"Akun staf ini sudah dinonaktifkan."` |
| `staff:admin,supervisor` (dst.) | `EnsureStaffRole` | Seperti di atas, ditambah `role` harus ada di daftar. Jika tidak: `403 "Peran Anda tidak memiliki akses ke fitur ini."` |
| `customer` | `EnsureCustomer` | Token harus milik `Customer` yang statusnya bukan `inactive`. Jika tidak: `403 "Fitur ini khusus untuk nasabah."` atau `"Rekening ini sudah tidak aktif."` |
| `throttle:login` | Rate limiter | 5 percobaan per menit per username + IP (staf) atau 30 per menit per IP (id_token nasabah) |
| `throttle:customer-activation` | Rate limiter | 20 per menit per IP |
| `throttle:customer-unlock` | Rate limiter | 5 per menit per nasabah (unlock & buat PIN) |
| `throttle:10,1` | Rate limiter | 10 koreksi per menit per teller |
| `throttle:withdrawal-authorization-*` | Rate limiter bernama | Batas permintaan otorisasi penarikan per aktor (lihat [API otorisasi penarikan](/api/withdrawal-authorizations/)) |

Middleware peran berjalan **sebelum** route model binding, sehingga pemanggil dengan
peran salah selalu mendapat `403` dan tidak dapat mengetahui apakah suatu id ada.
`tests/Feature/RoleAccessTest.php` memeriksa setiap endpoint untuk setiap aktor dan
memastikan setiap route API selain login punya `auth:sanctum` dan middleware aktor.

## Pemeriksaan di controller

| Pemeriksaan | Endpoint | Hasil |
| --- | --- | --- |
| Teller hanya melihat dan mencetak shift sendiri | `GET /teller/daily-reports/{id}`, `/export` | `404` untuk laporan teller lain |
| Teller hanya mencetak dan mengoreksi transaksi sendiri | `GET /teller/transactions/{id}/receipt`, `POST …/correct` | `404` |
| Daftar dibatasi ke pemanggil | `GET /teller/transactions`, `/teller/daily-reports`, `/teller/shift`, semua `/customer/*` | Hanya data sendiri; parameter tidak dapat memilih akun lain |
| Detail transaksi nasabah | `GET /customer/transactions/{id}` | `404` untuk transaksi nasabah lain |
| Permintaan penarikan (teller) | `/teller/withdrawal-authorizations/{id}[/cancel\|/complete]` | `404` untuk permintaan teller lain |
| Permintaan penarikan (nasabah) | `/customer/withdrawal-authorizations/{id}[/approve\|/reject]` | `404` untuk permintaan nasabah lain |
| Akun administrator dilindungi | `PUT/PATCH/DELETE /admin/staff/{id}`, `…/block`, `…/unblock` | `403 "Akun administrator tidak dapat diubah melalui API."` |
| Otorisasi koreksi | `POST /teller/transactions/{id}/correct` | Butuh `supervisor_username` + `supervisor_password` milik supervisor aktif (`422` jika salah) |

Catatan:

- **Supervisor dan koreksi.** Supervisor tidak pernah memanggil endpoint koreksi.
  Mereka mengotorisasi koreksi teller dengan mengetik username dan password sendiri
  di layar teller.
- **Tidak ada yang dapat** mengubah atau menghapus transaksi, baris jurnal, laporan
  yang sudah disetujui, atau pemindahan kas.
- **Mengganti password sendiri** tidak tersedia untuk siapa pun. Admin dapat mengatur
  password teller dan supervisor lewat `PATCH /admin/staff/{id}`.

## Pedoman untuk klien

- Tentukan rute berdasarkan `data.actor` dari respons login, lalu `data.user.role`.
- Aplikasi web staf sebaiknya menolak `actor: "customer"`, dan aplikasi mobile
  menolak `actor: "staff"`.
- Pada `401` atau `403` dari pemeriksaan peran, hapus token dan kembali ke halaman
  login (rubrik UKK 3.2). Satu-satunya `403` yang merupakan error bisnis biasa adalah
  `Akun administrator tidak dapat diubah melalui API.` saat mengubah staf.
