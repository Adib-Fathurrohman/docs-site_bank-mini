Every flow on this page is for the **administrator** only. Supervisors can read the
account and staff lists but cannot change them.

## Customer account lifecycle

### Opening an account

| | |
| --- | --- |
| Endpoint | `POST /api/admin/customers` |
| Preconditions | The major exists (`GET /api/majors`) |
| Input | `nis`, `full_name`, `email` (required, unique), `class` (`X`/`XI`/`XII`), `major_id`, `group` (`1`–`4`) |
| PIN rule | Admins **never set PINs**. Sending `pin` is refused (`422`). Students create their own PIN in the app |
| Process | `CustomerService::create` generates `{CODE}-{YEAR}-{SERIAL}` |
| Database effect | A `customers` row: status `active`, activation `pending`, balance `0`, `pin` null |
| Response | `201` Customer (`activation_status: "pending"`, `pin_set: false`) |
| Failures | `422` validation (NIS or email already taken, including closed accounts); `403` not an admin |

The opening balance is always `0`. Cash can be deposited at the counter immediately even before the student activates the mobile app.

### Importing customers from old bookkeeping

| | |
| --- | --- |
| Endpoint | `POST /api/admin/customers/import` |
| Input | `file` (required, `.xlsx`/`.csv`), `transactions_file` (optional, or a `Transaksi` sheet) |
| Capacity | Up to 1,000 customers and 10,000 historical transaction rows |
| Customer columns | NIS, Name, Email (optional), Class, Major, Group, Balance (optional), Account Number (optional) |
| Transaction columns | NIS, Date, Type (`deposit`/`withdrawal`), Amount, Note |
| Opening balance | Any balance not explained by transactions becomes an opening deposit (*"Saldo awal dari pembukuan lama"*) |
| Database effect | Bulk `customers` creation; transactions linked to `customer_imports` (`daily_report_id: null`) |
| Atomicity | All or nothing: fails completely on invalid formatting, duplicate NIS, or negative balance |


### Editing data and suspending an account

| | |
| --- | --- |
| Endpoint | `PUT\|PATCH /api/admin/customers/{id}` |
| Input | Any subset of `nis`, `full_name`, `email`, `class`, `major_id`, `group`, `account_status` (`active`/`suspended` only) |
| Email rule | `email` can only be updated while activation is `pending`. Once activated, email is locked (`422`) |
| PIN rule | Sending `pin` is refused (`422`) — use the dedicated PIN reset endpoint |
| Cannot change | Account number and balance. Changing the major does not change the number |
| Failures | `422` validation; `404` account is closed |

Suspending an account does not revoke existing customer tokens, but prevents any withdrawals.

### Resetting customer PIN

| | |
| --- | --- |
| Endpoint | `POST /api/admin/customers/{id}/pin-reset` |
| When to use | Customer forgot their PIN |
| Effect | Clears `pin`, sets `pin_failed_attempts = 0`, and clears `pin_locked_until` (lifts any lock) |
| Next step | Customer signs into the app via Firebase, then sets up a new PIN via `POST /api/customer/pin/setup` |
| Response | `200` with updated Customer object (`pin_set: false`) |

### Closing an account (graduation)

| | |
| --- | --- |
| Endpoint | `POST /api/admin/customers/{id}/deactivate` |
| Process | One database transaction: status `inactive`, delete all customer tokens, disable user in Firebase, soft delete |
| Validation | No balance check |
| Effect | `deleted_at` is set. Transactions and journal lines are untouched |
| Failures | `404` if already closed |

<Aside type="caution" title="Pay out the balance first">
Closing does not require a zero balance and cannot be undone. Any remaining balance
must be withdrawn through a teller **before** the account is closed, and the
minimum-balance rule still applies (limitation L5).
</Aside>

Closed accounts remain readable through `GET /api/customers?trashed=with|only`,
`GET /api/customers/{id}`, the statement PDF and the audit log.

### Customer card data

`GET /api/admin/customers/{id}/card` returns the data to print the card, including
`qr_payload` (`BANKMINI:{account_number}`). The backend does not generate QR images;
the client renders the payload as a QR code.

## Staff management

| Flow | Endpoint | Database effect | Notable failures |
| --- | --- | --- | --- |
| Create a teller/supervisor | `POST /api/admin/staff` | A `users` row (password hashed, `is_active` true) | `422` (role `admin` refused, duplicate username) |
| Edit staff | `PUT\|PATCH /api/admin/staff/{id}` | `users` update (including password, role teller↔supervisor) | `403` for admin accounts |
| Block | `POST /api/admin/staff/{id}/block` | `is_active` false, all tokens deleted | `403` for admin accounts |
| Unblock | `POST /api/admin/staff/{id}/unblock` | `is_active` true | `403` for admin accounts |
| Delete | `DELETE /api/admin/staff/{id}` | Row and tokens deleted if nothing references it | `409` when transactions, reports, approvals or settings changes reference it |
| Import | `POST /api/admin/staff/import` (multipart `file`) | All rows inserted in one database transaction; missing passwords are generated and returned once | `422` keyed `rows.{i}.{field}`; nothing is inserted |

<Aside type="note" title="Block, don't delete">
A staff member who has recorded transactions cannot be deleted, because their history
must keep pointing at their account (`ON DELETE RESTRICT`). Block the account instead.
</Aside>

## Not available

- Restoring a closed account; closing with an automatic pay-out.
- Managing administrator accounts through the API (including admin passwords).
- Managing majors through the API (seeded, read-only).
- Staff changing their own password.

Full endpoints: [Admin API](/en/api/admin/).
