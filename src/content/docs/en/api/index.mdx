The backend provides **83 JSON routes** under `/api` (80 distinct paths; `PUT|PATCH`
share a route on customers and settings). The list at the bottom of this page is generated from
`docs/API_SUMMARY.json`, which is built from `php artisan route:list`.

## Conventions

| Item | Rule |
| --- | --- |
| Base URL | `http://localhost:8000/api` in development (the app's host + `/api`) |
| Headers | Always `Accept: application/json`; `Content-Type: application/json` with a body; `Authorization: Bearer <token>` everywhere except login |
| Money | Integer Rupiah, no decimals (`50000` = Rp50.000) |
| Timestamps | ISO 8601 in UTC, e.g. `2026-10-27T13:10:36.000000Z` (= 20:10 WIB). Convert to local time in the client |
| Dates | `YYYY-MM-DD` in the school's timezone (Asia/Jakarta). Audit filters also accept `YYYY-MM-DD HH:MM` |
| Single objects | Wrapped in `data` |
| Lists | A `data` array plus `links` and `meta` |
| PDFs | `Content-Type: application/pdf` and `Content-Disposition: attachment; filename=...` |
| Message language | Business-rule messages are Indonesian; field validation messages are Laravel's English defaults |
| Secrets | Passwords, PINs and idempotency keys never appear in responses |

<Aside type="note" title="About the examples in this reference">
Example responses were captured from real requests against the **demo** database
(seeder); names and amounts are fictitious. Long lists are shortened, and
`"...": "..."` marks omitted fields. Tokens are written as `<token>`.
</Aside>

## Pagination

Lists accept `?page=` (default 1) and `?per_page=` (1–100, clamped; the default differs
per endpoint).

```json
{
  "data": [ "..." ],
  "links": { "first": "...?page=1", "last": "...?page=2", "prev": null, "next": "...?page=2" },
  "meta": { "current_page": 1, "from": 1, "last_page": 2, "path": "...", "per_page": 15, "to": 15, "total": 22 }
}
```

There are no sort parameters; each endpoint has a fixed order.

| Field | Values |
| --- | --- |
| Staff `role` | `admin`, `supervisor`, `teller` |
| Customer `account_status` | `active` (can transact), `suspended` (can log in and view, cannot transact), `inactive` (graduated: cannot log in, soft deleted) |

## Rate limits

| Limiter | Routes | Limit | Key |
| --- | --- | --- | --- |
| `login` | `POST /login`, `/staff/login`, `/customer/login` | 5 per minute | username/identifier (lowercased) + IP |
| `throttle:10,1` | `POST /teller/transactions/{id}/correct` | 10 per minute | teller |
| `withdrawal-authorization-create` | `POST /teller/withdrawal-authorizations` | 10 per minute | teller |
| `withdrawal-authorization-poll` | list/show/cancel/complete (teller), list/show (customer) | 120 per minute | actor |
| `withdrawal-authorization-decide` | approve/reject (customer) | 5 per minute | customer |

Going over a limit returns `429 {"message":"Too Many Attempts."}`. The authorization
limiter keys include the actor type, so a teller and a customer with the same numeric
id never share a counter.
