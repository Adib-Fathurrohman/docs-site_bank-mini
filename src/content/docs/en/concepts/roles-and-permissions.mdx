## Four layers of checks

| Layer | Question | Where | On failure |
| --- | --- | --- | --- |
| **Authentication** | Who is calling? | `auth:sanctum` on every route except login | `401 Unauthenticated.` |
| **Authorization** | May this actor/role call this endpoint? Is this record theirs? | `staff`, `staff:{roles}`, `customer` middleware; ownership checks in controllers | `403` (role) or `404` (not theirs) |
| **Business rules** | Is the action allowed in the current state? | Services (shift state, balance, PIN, report status, …) | `422` |
| **Client visibility** | Which menus and buttons to show? | React / Expo code | — |

<Aside type="danger" title="Hiding a button is not security">
Every request is re-checked by the backend against the database (role and
`is_active` are read fresh for every token). Clients only mirror the backend rules so
users do not see pages that would fail.
</Aside>

## Actors and models

Staff and customers are **different tables and models**. A customer is not a `users`
row and has no `role`.

| Actor | Model | `role` value | Notes |
| --- | --- | --- | --- |
| Administrator | `App\Models\User` | `admin` | Created by the seeder; cannot be created, edited, blocked or deleted through the API |
| Supervisor | `User` | `supervisor` | |
| Teller | `User` | `teller` | Usually a student on duty (`class`, `phone` fields) |
| Customer (*nasabah*) | `App\Models\Customer` | — | Students; log in with NIS/account number + PIN |

Each staff member has exactly one role. Multi-role users are not supported.

## Middleware

| Middleware | Class | Effect |
| --- | --- | --- |
| `auth:sanctum` | Laravel Sanctum | Requires a valid, unexpired bearer token. Otherwise `401 {"message":"Unauthenticated."}` |
| `staff` | `EnsureStaffRole` | The token must belong to a `User` with `is_active = true`. Otherwise `403 "Fitur ini khusus untuk staf bank."` or `"Akun staf ini sudah dinonaktifkan."` |
| `staff:admin,supervisor` (etc.) | `EnsureStaffRole` | As above, plus `role` must be in the list. Otherwise `403 "Peran Anda tidak memiliki akses ke fitur ini."` |
| `customer` | `EnsureCustomer` | The token must belong to a `Customer` whose status is not `inactive`. Otherwise `403 "Fitur ini khusus untuk nasabah."` or `"Rekening ini sudah tidak aktif."` |
| `throttle:login` | Rate limiter | 5 attempts per minute per username/identifier + IP |
| `throttle:10,1` | Rate limiter | 10 corrections per minute per teller |
| `throttle:withdrawal-authorization-*` | Named rate limiters | Withdrawal authorization request limits per actor (see [Withdrawal authorization API](/en/api/withdrawal-authorizations/)) |

The role middleware runs **before** route model binding, so a caller with the wrong
role always gets `403` and cannot learn whether an id exists.
`tests/Feature/RoleAccessTest.php` checks every endpoint for every actor and verifies
that every API route except login has `auth:sanctum` and an actor middleware.

## Controller-level checks

| Check | Endpoints | Result |
| --- | --- | --- |
| Tellers only see and print their own shifts | `GET /teller/daily-reports/{id}`, `/export` | `404` for other tellers' reports |
| Tellers only print and correct their own transactions | `GET /teller/transactions/{id}/receipt`, `POST …/correct` | `404` |
| Lists are scoped to the caller | `GET /teller/transactions`, `/teller/daily-reports`, `/teller/shift`, all `/customer/*` | Own data only; parameters cannot select another account |
| Customer transaction detail | `GET /customer/transactions/{id}` | `404` for other customers' transactions |
| Withdrawal requests (teller) | `/teller/withdrawal-authorizations/{id}[/cancel\|/complete]` | `404` for other tellers' requests |
| Withdrawal requests (customer) | `/customer/withdrawal-authorizations/{id}[/approve\|/reject]` | `404` for other customers' requests |
| Administrator accounts are protected | `PUT/PATCH/DELETE /admin/staff/{id}`, `…/block`, `…/unblock` | `403 "Akun administrator tidak dapat diubah melalui API."` |
| Correction authorization | `POST /teller/transactions/{id}/correct` | Needs `supervisor_username` + `supervisor_password` of an active supervisor (`422` otherwise) |

Notes:

- **Supervisors and corrections.** A supervisor never calls the correction endpoint.
  They authorize a teller's correction by typing their own username and password on
  the teller's screen.
- **Nobody** can edit or delete transactions, journal lines, approved reports or cash
  transfers.
- **Changing your own password** is not available to anyone. An admin can set
  tellers' and supervisors' passwords with `PATCH /admin/staff/{id}`.

## Guidance for clients

- Route by `data.actor` from the login response, then by `data.user.role`.
- The staff web app should refuse `actor: "customer"`, and the mobile app should
  refuse `actor: "staff"`.
- On `401`, or a `403` from a role check, delete the token and return to the login
  page (UKK rubric 3.2). The only `403` that is a normal business error is
  `Akun administrator tidak dapat diubah melalui API.` when editing staff.
