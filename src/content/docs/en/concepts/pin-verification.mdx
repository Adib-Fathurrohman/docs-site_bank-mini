A customer PIN is 6 digits. It is used to unlock the app session, authorize withdrawals,
and change the PIN. **The PIN is not a login credential** (customers log in using Firebase
Authentication). Every PIN check runs in **one place**:
`App\Services\PinService::verify()`.

## Storage and ownership

- `customers.pin` is cast `hashed` (bcrypt, `BCRYPT_ROUNDS=12`) and is a hidden
  attribute (`$hidden`). No resource, error message or log contains the PIN.
- The `pin` column is **nullable**: every new account is created without a PIN (`pin_set: false`).
- A database check constraint enforces `CHECK (pin IS NULL OR activated_at IS NOT NULL)`: a PIN
  can only exist on an activated account.
- **The admin never sets a PIN.** The customer creates their own PIN in the Bank Mini mobile app
  after activation (`POST /api/customer/pin/setup`), supplying a fresh Firebase ID token to prove identity.
- Before a customer creates a PIN, any action requiring a PIN is refused with status **422**
  and error code `pin_not_set` without counting failed attempts.
- **Two routes for forgotten PINs:**
  1. **Direct Admin Reset:** An administrator resets the PIN directly in the admin portal (`POST /api/admin/customers/{id}/pin-reset`). This clears the PIN, removes locks, and cancels any open self-service request.
  2. **Self-Service Request (v0.2.1):** The customer requests a reset in the mobile app (`POST /api/customer/pin-reset-requests`) using fresh Firebase re-authentication. Requires admin approval and a 24-hour safeguard delay (`BANK_PIN_RESET_WAIT_HOURS`) before the new PIN can be set. While open, withdrawals are paused (**422** `pin_reset_in_progress`).

## The shared PIN lock

<Mermaid
	caption="The wrong-PIN counter. Three mistakes in a row anywhere lock the PIN everywhere."
	chart={`stateDiagram-v2

  [*] --> Normal
  Normal --> Normal: correct PIN (counter reset to 0)
  Normal --> Wrong1: wrong PIN
  Wrong1 --> Wrong2: wrong PIN
  Wrong1 --> Normal: correct PIN
  Wrong2 --> Locked: 3rd wrong PIN
  Wrong2 --> Normal: correct PIN
  Locked --> Normal: 15 minutes pass or admin resets the PIN
  note right of Locked
    Even the correct PIN is refused.
    pin_locked_until = now + 15 minutes
  end note`}
/>

| Rule | Value |
| --- | --- |
| Mistakes before the lock | 3 in a row (`BANK_PIN_MAX_ATTEMPTS`) |
| Lock duration | 15 minutes (`BANK_PIN_LOCK_MINUTES`) |
| Applies to | App unlock, withdrawal approval in the app, withdrawal with the PIN at the counter, PIN change |
| Counter reset | A correct PIN, or the admin resetting the PIN |
| Columns | `pin_failed_attempts`, `pin_locked_until` |

`PinService::verify()` runs in **its own database transaction** with a row lock on
the customer, so a wrong attempt is saved even though the request fails. Callers with a
bigger transaction (approval, counter withdrawal) call it **before** that transaction.

<Aside type="caution" title="One lock everywhere">
Three wrong PINs at app unlock also lock withdrawal approval and counter withdrawals.
</Aside>

### Responses when a PIN is wrong or not set

When a PIN has not yet been set (`pin_set: false`):

```json title="422 Unprocessable Entity"
{
  "message": "Nasabah belum membuat PIN. PIN dibuat oleh nasabah di aplikasi Bank Mini setelah akun diaktifkan.",
  "code": "pin_not_set"
}
```

When a wrong PIN is submitted:

```json title="422 Unprocessable Entity (attempt 1 or 2)"
{ "message": "PIN salah. Sisa percobaan: 2.", "remaining_attempts": 2, "pin_locked_until": null }
```

When locked (`pin_locked_until` in UTC, the message in WIB):

```json title="422 Unprocessable Entity (locked)"
{
  "message": "PIN diblokir sementara karena terlalu banyak percobaan salah. Coba lagi pukul 20:25.",
  "remaining_attempts": 0,
  "pin_locked_until": "2026-10-27T13:25:37.830610Z"
}
```

## Two withdrawal authorization modes

Every withdrawal needs the customer's PIN. **Who types the PIN, and on which device**,
depends on the `withdrawal_verification` setting.

| Mode | Setting value | How it works | Endpoints |
| --- | --- | --- | --- |
| **A · Approval in the app** (default) | `mobile` or `both` | The teller creates a request; the customer approves it with their PIN on their own phone; the teller completes it. The teller never sees or sends the PIN | `/api/teller/withdrawal-authorizations`, `/api/customer/withdrawal-authorizations` |
| **B · PIN at the counter** | `terminal` or `both` | The customer types the PIN on the teller's screen; the withdrawal runs in one request | `POST /api/teller/withdrawals` |

<Mermaid
	caption="The withdrawal_verification setting decides which mode is active."
	chart={`flowchart LR
  S{"withdrawal_verification"} -- "mobile" --> A["Mode A only"]
  S -- "terminal" --> B["Mode B only"]
  S -- "both" --> AB["Mode A or B"]
  A --> A1["POST /teller/withdrawals<br/>refused 422"]
  B --> B1["POST /teller/withdrawal-authorizations<br/>refused 422"]`}
/>

Mode B is off by default because the PIN passes through the teller's client. Mode B
also has limitation **L2**: the PIN is checked before the shift, account status and
balance, so a wrong PIN still counts even when the withdrawal would fail anyway. Mode
A does not have this problem because everything is checked when the request is
created.

## Not available

- Forgot-PIN by the customer. PINs are reset by the admin.
- Push notifications for withdrawal requests (polling is used).
- Approval in the app for deposits or corrections (withdrawals only).
- Per-device customer tokens: any device where the customer is logged in can approve.
