## Keterbatasan backend

Perilaku saat ini yang belum diperbaiki. Penomoran mengikuti
`docs/BACKEND_CHECKPOINT.md`; *terverifikasi* berarti dikonfirmasi dengan menjalankan
kode.

| # | Keterbatasan | Dampak bagi klien |
| --- | --- | --- |
| L1 | Nominal tidak wajib kelipatan 100, padahal uang dihitung dalam pecahan ≥ Rp100. Nominal seperti Rp150 membuat shift tidak dapat ditutup sampai dikoreksi (*terverifikasi*) | Paksa kelipatan Rp100 di klien teller |
| L2 | Mode B (`POST /teller/withdrawals`) memeriksa PIN sebelum shift, status, dan saldo | Di mode `terminal`, periksa dulu `can_transact`, status, saldo, dan `pin_locked_until` |
| L3 | Shift yang ditolak masih menampilkan `physical_balance`, `difference`, dan `closing_counts` lama sampai ditutup lagi (*terverifikasi*) | Untuk `status = rejected`, abaikan atau beri label "hitungan sebelumnya" |
| L4 | CORS tidak mengekspos header respons (`Idempotent-Replayed`, `Content-Disposition`) | Bedakan ulangan dengan `201`/`200`; beri nama PDF di klien; atau pakai proxy same-origin |
| L5 | Menutup rekening tidak butuh saldo nol dan tidak dapat dibatalkan | Peringatkan sebelum menutup rekening bersaldo |
| L6 | Staf tidak dapat mengganti password sendiri; akun admin tidak dapat diubah lewat API | Jangan buat halaman "ganti password" untuk staf |
| L7 | Tidak ada refresh token (8 jam untuk staf, 30 hari untuk nasabah) | Login ulang saat `401` |

| L9 | Bahasa campuran: pesan bisnis Indonesia, pesan validasi Inggris | Petakan pesan field jika butuh satu bahasa |
| L10 | Laporan tahunan, jurnal, dan ekspor audit hanya PDF | Bangun tabel dari JSON `/audit/*` |
| L11 | Nilai filter `/customers` dan `/staff` tidak divalidasi | Pakai dropdown bernilai tetap |
| L12 | `qr_scanner_mode` hanya disimpan; lookup tetap menerima QR walau mode `disabled` | Klien yang menentukan apa yang ditawarkan |
| L13 | Jurusan tidak dapat dikelola lewat API | Dropdown hanya baca |
| L14 | Teller hanya dapat mencari satu nasabah; tidak ada daftar rekening untuk teller | Tidak ada penelusuran rekening untuk teller |

| L16 | Idempotency key tidak pernah kedaluwarsa | Buat kunci baru per transaksi |
| L17 | Payload QR tidak ditandatangani; hanya mengidentifikasi | Penarikan selalu butuh PIN |
| L18 | Tidak ada parameter urutan di daftar mana pun | Terima urutan server |
| L19 | Notifikasi push FCM hanya untuk otorisasi penarikan baru; event lain mengandalkan polling atau refresh manual | Daftarkan FCM token via `/api/customer/push-tokens` dan tangani polling cadangan |
| L20 | Token nasabah tanpa ability | Opsional: biometrik sebelum PIN pad |
| L21 | Rekening ditutup antara persetujuan dan penyelesaian membuat `complete` menjawab `404` | Tampilkan pesan; mulai ulang |

## Inkonsistensi yang tercatat

Dari `docs/FRONTEND_HANDOFF.md` §19.

| # | Hal | Status |
| --- | --- | --- |
| I1 | Matriks soal UKK tidak memberi admin akses "input transaksi" dan memberi akses baca jurnal. Backend juga membiarkan admin membaca log transaksi | Diterapkan seperti dijelaskan |
| I2 | `POST /staff/login` dan `/customer/login` menduplikasi `POST /login` | Pakai `/login` saja |
| I3 | Pesan login `Rekening ini sudah tidak aktif.` praktis tidak pernah muncul (rekening `inactive` selalu di-soft delete) | Perlakukan keduanya sebagai login gagal |

| I5 | Unlock aplikasi (`POST /customer/unlock`) adalah pengaman UI sisi klien | Token Sanctum yang valid tetap dapat dipakai memanggil API perbankan meskipun aplikasi belum di-unlock |
| I6 | Wawancara UKK menanyakan peran Customer Service/Akuntansi dan produk tabungan siswa vs pegawai; backend menerapkan empat peran soal dan satu produk tabungan (akun 201) | Belum tersedia |

## Belum tersedia

Fitur berikut **tidak ada** di backend. Jangan membangun antarmuka untuknya.

- Pendaftaran mandiri nasabah; transaksi yang dimulai nasabah; transfer antar-rekening.
- Pinjaman, deposito berjangka, produk tabungan selain akun 201, biaya administrasi.
- Memulihkan rekening yang ditutup; penutupan dengan pembayaran otomatis.
- Koreksi sebagian; mengubah atau menghapus transaksi.
- Persetujuan laporan massal; delegasi persetujuan.
- Pemindahan kas dari brankas ke teller.
- Lupa password staf mandiri; staf mengganti password sendiri; mengelola akun admin.
- Manajemen jurusan; pengguna dengan banyak peran; integrasi absensi.
- Notifikasi push untuk transaksi umum selain otorisasi penarikan (misalnya setoran masuk atau pembaruan saldo langsung).
- Persetujuan di aplikasi untuk setoran atau koreksi (hanya penarikan).
- Laporan tahunan versi JSON; gambar QR dari server.
- Daftar otorisasi penarikan untuk admin atau supervisor.
